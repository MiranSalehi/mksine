# Form hooks

Form hooks let you append, modify, or replace components in a Filament form **without editing the resource that owns the form**. They are the primary extension point for Filament 4 schemas inside MKSine.

There are two equivalent registration models:

- **Class-based, discoverable** — implement `FormHookListenerInterface` and let `mks:discover` index it. This is what the package does for its own resources.
- **Closure-based, runtime** — call `Hooks::extendForm($name, $callback)` from a plugin’s `boot()`. No DB row, no admin toggle.

Choose whichever matches your operational needs ([overview](overview-two-families.md)).

## How a form gets hooked

When a Filament resource is generated by `mks-plugin:make-resource`, the scaffold ends with:

```php
public static function form(Schema $schema): Schema
{
    $schema = $schema
        ->components([
            // …default fields…
        ]);

    return app(\Miran\Mksine\Core\Hooks\FormHookManager::class)
        ->apply('post.form', $schema);
}
```

`FormHookManager::apply($formName, $schema)` walks every callable registered for `$formName`, in registration order, and feeds each one the **current** `$schema`. The callable returns a (possibly modified) `Schema`. If it returns anything else, the modification is dropped and a warning is logged. Exceptions inside a callable are caught, logged via `Log::error()`, and **execution continues** with the next callable. This is intentional: one buggy plugin should not blank out a form for everyone.

## Class-based listener

```php
<?php

declare(strict_types=1);

namespace Acme\MyPlugin\Hooks\Forms;

use Filament\Forms\Components\TextInput;
use Filament\Schemas\Components\Section;
use Filament\Schemas\Schema;
use Miran\Mksine\Core\Hooks\FormHookListenerInterface;

final class ExtendPostFormListener implements FormHookListenerInterface
{
    public static function getFormName(): string
    {
        return 'post.form';
    }

    public static function getPriority(): int
    {
        return 0;
    }

    public static function extend(Schema $schema): Schema
    {
        $existing = method_exists($schema, 'getComponents') ? $schema->getComponents() : [];

        return $schema->components([
            ...$existing,
            Section::make('SEO')
                ->schema([
                    TextInput::make('seo_title')->maxLength(120),
                    TextInput::make('seo_description')->maxLength(255),
                ])
                ->collapsible()
                ->collapsed(),
        ]);
    }
}
```

Place the file under a directory that `mks:discover` scans (your plugin’s `src/Hooks/Forms/`, registered in `mksine.hooks.discovery_paths`). Then run:

```bash
php artisan mks:discover
```

The class is recorded in `mks_hooks` for inventory. **Execution still flows through `FormHookManager::apply()`** — the database row is metadata, not the dispatch path.

> The current discovery service indexes form/table listeners; toggling `is_enabled` for a form/table row in `mks_hooks` is **not** honoured by `FormHookManager::apply()`. If you need the ability to disable a form hook from the admin, use a class with an internal feature-flag check inside `extend()`, or use a runtime registration that you can guard with a config check.

## Runtime registration

```php
use Miran\Mksine\Core\Hooks\Hooks;
use Filament\Forms\Components\TextInput;

public function boot(): void
{
    Hooks::extendForm('post.form', function ($schema) {
        $existing = method_exists($schema, 'getComponents') ? $schema->getComponents() : [];

        return $schema->components([
            ...$existing,
            TextInput::make('canonical_url')->url()->maxLength(255),
        ]);
    });
}
```

Same `FormHookManager` under the hood, no class, no `mks_hooks` row.

## Form names

Form names are **conventional**, not enforced. The package and scaffolds use `'<resource>.form'` (e.g. `post.form`, `category.form`). Plugin authors should follow the same pattern (`'<plugin-id>::<resource>.form'` if you want to namespace explicitly to avoid collisions).

There is no central registry of names — if you typo `'post.from'`, the callback simply never runs and you get no error. Add a smoke test that asserts your hook fires, or document your form names in your plugin’s README.

## Replacing vs appending

Filament 4’s `Schema::components([...])` **replaces** the component list. Always read the existing components first if you want to append:

```php
$existing = method_exists($schema, 'getComponents') ? $schema->getComponents() : [];

return $schema->components([
    ...$existing,
    // your additions
]);
```

If you intentionally want to replace the schema (for example, a plugin that turns the post form into something else entirely), call `components([…])` without spreading `$existing`. Document this loudly: it’s a foot-gun for the next plugin author who tries to extend the same form.

## Ordering

Two ordering layers exist:

1. The **callback registration order** — first registered, first executed.
2. The class-based `getPriority()` — `mks:discover` records it, but the runtime apply loop still executes in **registration order**, not priority order. If you need deterministic priority for form hooks, register them via runtime hooks in a deterministic boot sequence (e.g. ordered by plugin manifest) or accept that the order is _whichever plugin booted first_.

This is a real limitation; do not pretend otherwise to plugin consumers.

## Where to put the namespace

Plugins ship form-related views/components alongside the listener. The recommended layout:

```
{plugin_root}/my-plugin/src/Hooks/Forms/
{plugin_root}/my-plugin/resources/views/forms/
{plugin_root}/my-plugin/lang/en/forms.php
```

Keep the listener thin (it returns a schema) and push real UI/logic into Blade components or services your listener calls.
