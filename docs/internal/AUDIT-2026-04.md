## Hook discovery (`mks:discover`)

**Source of truth:** `DiscoverHooksCommand::resolveDiscoveryPaths()`.

1. Always scans: `packages/mksine/src/Core/Listeners` (package core).
2. Additionally scans each existing directory in `config('mksine.hooks.discovery_paths')` (see `config/mksine.php`). Paths can be absolute or relative via `base_path()`.

**Implication for plugins:** Class-based `MksineListenerInterface` / form / table listeners **outside** core **are not** discovered unless their directory is listed in `discovery_paths` (host `config/mksine.php` or a service provider merging config). The old README/skill wording implied “plugins might not sync” — the accurate rule is: **no path, no DB sync**.

**Runtime hooks:** `Hooks::`, `ResourceHookManager`, `theme_add_action` — **not** `mks_hooks` (see [20-hooks-contract.md](../20-hooks-contract.md)).

## Plugin lifecycle (code)

**Source of truth:** `Mksine\Core\Plugins\PluginManager`.

- `initialize()` → register PSR-4 autoload from manifests, load registry.
- `bootPlugins()` → for each active plugin: instantiate via `PluginLifecycle`, call `boot()`, load web routes if present.
- Boot failures → logged, DB row `markBootFailed`, plugin effectively disabled.

Manifest: `{plugin_root}/{id}/plugin.php` (`{plugin_root}` = `base_path(config('mksine.plugins_path'))`) → `PluginDiscovery` builds `PluginManifest`; `plugin_class` must implement `PluginInterface`.
